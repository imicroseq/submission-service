Reviewed PR #27's second revision (duplicate sequencing-file submission). Seven of ten earlier findings resolved, two of the fixes better than what was suggested: the intra-batch duplicate check moved to the controller so it covers both submission paths from one place, and `buildSubmissionFileMetadata` was replaced with a single database read instead of N serial Song calls. Two open questions were raised on the PR rather than here, since they are decisions rather than debt: whether existing `record_analysis_map` rows get an `md5_sum` backfill (without one the check is forward-only and catches nothing already submitted), and whether the initial-upload path stays outside the cross-submission duplicate check.

- `.dev/tech-debt.md`: six auth entries added. The read-authorization gap, a possible cross-service token-confusion risk from the missing `iss`/`aud` check, write authorization being an unenforced convention across three call sites, the `allowedReadOrganizations` empty-collection ambiguity, a verify-then-decode fragility, and a reindex-lag window that opens once access levels become mutable.

The read-authorization entry needed a correction after the developer reviewed it. Every record in production being open today is a property of the current data, not the intended access model: access level is meant to be assigned per submission, at submission time or after, and future submissions will carry restricted access. Enforcement therefore has to exist at both this service and the search layer, since gating one leaks through the other. The entry was rewritten from an open question into a confirmed requirement.

Sharpened the same entry again into separate requirements for authentication and authorization on reads, since the two need different fixes, and identified the query endpoint as the natural first enforcement point: it already authenticates its requester and has a single place to compose a filter.

- `.dev/docs/auth/`: added a section on caller-supplied SQON filters and one on the value trust boundary. The SQON section records that the filter machinery comes from Lyric rather than this repo, that the caller's SQON is the only filter with no hook to compose a server-side one onto it, that any organization named in the path has to be checked against the requester's entitlements, and that the operator set is narrower than the search layer's. The trust-boundary section records that submitted record values pass through this service unmodified, with validation stopping at headers and required-field presence, so exposure on that path depends on how the dependency constructs its queries. Written deliberately as a boundary to understand rather than a gap to close here, because sanitizing at ingestion would corrupt legitimate data to compensate for query construction that belongs downstream.

Reading Lyric's SQON translator to answer a question about shared filter representations surfaced a security issue in that dependency, which was reported to its owner and fixed there. Not recorded in this repo's tech-debt, since it is not this repo's. Two durable consequences were kept instead, and are the two doc sections above. The transferable lesson, which the owner applied: after fixing a reported instance, sweep for the same pattern before treating the fix as closed; the sweep found a second, more severe instance.
