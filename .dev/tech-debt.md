`handleSequencingMetadataSubmission` (`src/submission/submissionHandler.ts`) fetches a Submission's clinical records via `getSubmissionDetailsById` with `pageSize` set to the full record count, i.e. one unbounded query per append call. Raised during review of the sequencing-metadata-append feature since it's the same class of problem ("large submission") that motivates this feature in the first place. Per Lyric's current storage model, this isn't actually fixable here: Lyric stores a Submission's data as a single JSONB column, so there's no partial-fetch to page or stream against
fix: revisit once the Lyric dependency ships the version that gives more granular control over Submission data storage; until then there's no code change to make on this side
standalone: yes

The duplicate-md5/record-identifier check is read-then-decide with no lock or transaction around it: two concurrent requests submitting the same file can both read `record_analysis_map` before either has written its row, both pass the check, and both get submitted to Song, producing the exact duplicate this feature exists to prevent
fix: wrap the check-then-insert sequence in a transaction at an appropriate isolation level (e.g. `SERIALIZABLE`) or an advisory lock keyed on `(submission_id, md5_sum)`. A DB-level `UNIQUE` constraint isn't an option: `SEQUENCING_SUBMISSION_ALLOW_DUPLICATES` makes duplicate MD5 sums legal by configuration, and a schema constraint can't be conditional on an environment variable. The `md5_sum` column and its index (`record_analysis_map.ts`) make this cheap to add now
standalone: yes

Duplicate MD5 detection is forward-only: `record_analysis_map` rows written before the `md5_sum` column existed have it as `NULL`, and the duplicate check skips falsy MD5 values to avoid false positives, so resubmitting any file that was submitted before this feature deployed passes uncaught
fix: backfill `md5_sum` for existing rows from Song (`getAnalysisById(...).files[0].fileMd5sum`, the same field `buildSubmissionFileMetadata` already reads) via a one-off migration or script
standalone: yes
`allowedReadOrganizations` (`src/middleware/verifyEgoJwt.ts`) is hardcoded to an empty array; nothing reads it yet, but once a read-side authorization check is implemented against it, an empty collection is ambiguous between two meanings that need distinct representations: "no restriction configured" versus "restricted to nothing." Flagged during cross-project auth design discussion with Arranger/Usher: their own audit found that in Elasticsearch query construction, three of four idiomatic ways to encode "no grants" compile to match-all rather than match-nothing (a clause-less boolean is match-all, and query optimizers can flatten it out of the tree entirely), so this exact ambiguity is a live, previously-confirmed failure mode elsewhere in the same platform, not a hypothetical one
fix: before implementing the read side, decide the representation for "no restriction" (e.g. `null`/`undefined`) versus "restricted to nothing" (e.g. `[]`) explicitly, and ensure whatever check consumes `allowedReadOrganizations` treats an empty array as fail-closed (deny all), not as an absence of restriction
standalone: yes

Read requests currently have no authorization at any layer, by default configuration, live today, not a design gap for future work. Three independent facts compose: `AUTH_PROTECT_METHODS` defaults to `POST,PUT,DELETE`, so `GET` bypasses `authMiddleware` entirely even with `AUTH_ENABLED=true`; the read controllers (`byCategory`/`bySystemId`/`byOrganization`/`byQuery` in `submittedData.ts`, `getSubmissionById`) perform no per-organization check, unlike the three write controllers; and `allowedReadOrganizations` is hardcoded to `[]` regardless. The layer that would authenticate is skipped before the layer that would scope is ever consulted. Surfaced during cross-project auth design review with Arranger; each fact was already documented individually, the composite wasn't
fix: resolved by the developer directly (2026-08-19): every record currently in iMS prod happens to be "open" today, but that's a snapshot of current data, not the permanent access model. Access level (who, what they're allowed to do) is meant to be defined per submission, at submission time or afterwards, and future submissions will carry restricted, authorized-eyes-only access. That means real read-authorization enforcement is needed at both the Lyric/submission-service layer (this repo) and the Arranger layer, not either alone: gating only one leaks through the other. Usher's public-by-default-unless-embargo framing (`permissions-model.md`) describes today's data, not the target model, and doesn't resolve this on its own. Actual fix: implement `allowedReadOrganizations` (or its Usher-grants equivalent) as a real, enforced per-organization/per-submission check on every read controller in this service, coordinated with Arranger's own filter enforcement so neither layer is the unguarded one
standalone: no

`AUTH_PUBLIC_KEY` verification checks the JWT signature only; there is no `iss`/`aud` check, so any token signed by the same key pair is accepted regardless of which service or audience it was actually issued for. If the EGO deployment uses one signing key platform-wide (unconfirmed, deployment fact, not in this repo), a token minted for a different Overture service would be accepted here with its scopes intact, a live cross-service token-confusion risk independent of the EGO/Usher migration. If EGO issues per-audience keys, this is a non-issue as-is
fix: confirm with whoever manages the EGO deployment whether signing keys are shared across services or per-audience. If shared, add an `audience`/`issuer` check to `jwt.verify` (`verifyEgoJwt.ts`) before relying on this token for authorization
standalone: no

`hasUserWriteAccess` is called ad hoc at three separate call sites (`src/controllers/submission/submit.ts:56`, `commit.ts:60`, `editData.ts:65`) rather than through a seam a new write path can't bypass by omission. A fourth write controller added later is authorized by nobody unless its author remembers to add the call, and nothing fails if they don't; the failure mode is silent, not an error. Same root-cause shape independently found in Arranger's own access-control audit (three read paths that simply never composed its filter): authorization implemented as a convention call sites follow, not a structural requirement they can't skip
fix: worth considering for the Usher integration specifically, build the seam so a handler cannot run without an authorization decision (e.g. router-level middleware or a wrapper the route registration itself requires) rather than adding another same-shaped call to a fourth controller
standalone: no

`verifyJwtToken` (`src/middleware/verifyEgoJwt.ts`) calls `jwt.verify(...)` and discards its return value, then separately calls `jwtDecode(token)` on the raw token to get the payload actually used downstream. Not currently exploitable, since decode only runs after verify succeeds on the same bytes, but it's a fragile coupling: if verification is ever made conditional, reordered, or its error caught and swallowed, the decode keeps working and silently supplies unverified data
fix: use `jwt.verify`'s own return value (it returns the decoded, verified payload) instead of a second, separate `jwtDecode` call. One-line change, no behavior change today, removes a future footgun
standalone: yes

Once per-submission access levels are settable after submission (per the developer's 2026-08-19 direction above), that setting becomes mutable, but Arranger's search index only reflects whatever it last indexed. An access-level change (open -> restricted) creates a window between the change and Maestro's next reindex where Arranger serves a stale, over-permissive decision, size unknown, depends on Maestro's reindex latency. Raised by Arranger during the same cross-project review; not fixable from this service alone, but this service is likely where the access-level change itself originates (a submission update), so it may be the one that needs to trigger a synchronous reindex or explicit cache invalidation rather than assuming the normal indexing pipeline catches it in time
fix: when designing where/how access-level changes get set, decide explicitly whether changing one requires this service to trigger an immediate reindex/invalidation signal rather than relying on Maestro's normal pipeline timing; needs coordination with whoever owns the Maestro indexing trigger, not a fix in this repo alone
standalone: no
