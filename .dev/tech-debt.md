SQON request validation depends on Lyric's `parseSQON` *throwing*, not on what it returns, and that boundary is scheduled to widen. `sqonSchema` (`src/common/validation.ts/common.ts:81-88`) is a zod `custom` validator whose entire body calls `parseSQON` inside a try/catch and discards the result, using throw versus no-throw as the validity signal. Lyric's own tracked work migrates `parseSQON` to `SqonBuilder.from()` from `@overture-stack/sqon` once that package leaves RC, and that function *normalizes* legacy operator aliases (`=`, `>=`, `filter` and others) rather than rejecting them. So inputs that are rejected today would start parsing successfully, and this service's request validation would silently widen to accept them. Nothing fails, nothing logs, and no type check on either side surfaces it, because the dependency is on exception behaviour rather than on a signature. Confirmed by Lyric and Maestro on 2026-09-29, who identified the specific trigger rather than leaving it hypothetical
fix: stop inferring validity from an exception. Validate the parsed structure this service actually requires (operators, field names, shape) rather than treating "did not throw" as sufficient, so the accepted set is defined here rather than inherited from a dependency's current strictness. Tracking it here rather than relying on being told when the migration lands, since by construction the change is invisible from this side
standalone: yes

Related to the entry above, same migration, different mechanism
fix: no change needed today. Worth a deliberate look at the migration rather than after it, to decide whether this service wants to keep inheriting the shape or pin its own

The duplicate-md5/record-identifier check is read-then-decide with no lock or transaction around it: two concurrent requests submitting the same file can both read `record_analysis_map` before either has written its row, both pass the check, and both get submitted to Song, producing the exact duplicate this feature exists to prevent
fix: wrap the check-then-insert sequence in a transaction at an appropriate isolation level (e.g. `SERIALIZABLE`) or an advisory lock keyed on `(submission_id, md5_sum)`. A DB-level `UNIQUE` constraint isn't an option: `SEQUENCING_SUBMISSION_ALLOW_DUPLICATES` makes duplicate MD5 sums legal by configuration, and a schema constraint can't be conditional on an environment variable. The `md5_sum` column and its index (`record_analysis_map.ts`) make this cheap to add now

fix: backfill `md5_sum` for existing rows from Song (`getAnalysisById(...).files[0].fileMd5sum`, the same field `buildSubmissionFileMetadata` already reads) via a one-off migration or script

`allowedReadOrganizations` (`src/middleware/verifyEgoJwt.ts`) is hardcoded to an empty array; nothing reads it yet, but once a read-side authorization check is implemented against it, an empty collection is ambiguous between two meanings that need distinct representations: "no restriction configured" versus "restricted to nothing." Flagged during cross-project auth design discussion with Arranger/Usher: their own audit found that in Elasticsearch query construction, three of four idiomatic ways to encode "no grants" compile to match-all rather than match-nothing (a clause-less boolean is match-all, and query optimizers can flatten it out of the tree entirely), so this exact ambiguity is a live, previously-confirmed failure mode elsewhere in the same platform, not a hypothetical one
fix: before implementing the read side, decide the representation for "no restriction" (e.g. `null`/`undefined`) versus "restricted to nothing" (e.g. `[]`) explicitly, and ensure whatever check consumes `allowedReadOrganizations` treats an empty array as fail-closed (deny all), not as an absence of restriction
standalone: yes

Read requests currently have no authorization at any layer, by default configuration, live today, not a design gap for future work. Three independent facts compose: `AUTH_PROTECT_METHODS` defaults to `POST,PUT,DELETE`, so `GET` bypasses `authMiddleware` entirely even with `AUTH_ENABLED=true`; the read controllers (`byCategory`/`bySystemId`/`byOrganization`/`byQuery` in `submittedData.ts`, `getSubmissionById`) perform no per-organization check, unlike the three write controllers; and `allowedReadOrganizations` is hardcoded to `[]` regardless. The layer that would authenticate is skipped before the layer that would scope is ever consulted. Surfaced during cross-project auth design review with Arranger; each fact was already documented individually, the composite wasn't
fix: resolved by the developer directly (2026-08-19): every record currently in iMS prod happens to be "open" today, but that's a snapshot of current data, not the permanent access model. Access level (who, what they're allowed to do) is meant to be defined per submission, at submission time or afterwards, and future submissions will carry restricted, authorized-eyes-only access. That means real read-authorization enforcement is needed at both the Lyric/submission-service layer (this repo) and the Arranger layer, not either alone: gating only one leaks through the other. Usher's public-by-default-unless-embargo framing (`permissions-model.md`) describes today's data, not the target model, and doesn't resolve this on its own. Actual fix: implement `allowedReadOrganizations` (or its Usher-grants equivalent) as a real, enforced per-organization/per-submission check on every read controller in this service, coordinated with Arranger's own filter enforcement so neither layer is the unguarded one. Requirements the Usher migration has to satisfy, carried by the submission-service bridge ticket (`imicroseq/roadmap#278`): (1) every read route, whatever the HTTP method, is served only through the bridge's principal, and a request without a credential receives only what the baseline (what Usher grants every requester) allows, which for this service may be nothing; whether reading submissions requires sign-in is decided in the baseline, not by refusing requests; (2) every read returns only what the requester's grants permit, including reads served by the Lyric routers this service mounts (submitted data, submission, audit), with an explicit decision on whether category and dictionary metadata stays public rather than inheriting whatever falls out; (3) a read by id checks the requester's entitlement to the record's organization before returning it, and answers a requester who is not entitled exactly as it answers for a record that does not exist; (4) the query endpoint composes the grant-derived filter with the caller's filter, and checks any organization named in the request against the requester's entitlements rather than treating it as scoping; (5) a requester whose grants reach nothing in this service receives nothing; (6) read responses expose submitter identity only to requesters entitled to it, which holds independently of whether the records themselves are open, and this service or its Lyric adapter enforces it, since the bridge does not filter response fields; (7) the submission-by-id event stream takes its credential in the `Authorization` header like every other route and never in a URL, so its client reads the stream with `fetch` rather than `EventSource`. The query endpoint is the natural first enforcement point, since it already authenticates and has a single place to compose a filter. Verify by: for every read route, the mounted Lyric ones included, a request without a credential receives only what the baseline allows, a requester whose grants reach nothing here receives nothing, a requester not entitled to a record gets the same answer as for a record that does not exist, and a requester entitled to one organization never receives another organization's records or submitter identity outside it
standalone: no

`AUTH_PUBLIC_KEY` verification checks the JWT signature only; there is no `iss`/`aud` check, so any token signed by the same key pair is accepted regardless of which service or audience it was actually issued for. If the EGO deployment uses one signing key platform-wide (unconfirmed, deployment fact, not in this repo), a token minted for a different Overture service would be accepted here with its scopes intact, a live cross-service token-confusion risk independent of the EGO/Usher migration. If EGO issues per-audience keys, this is a non-issue as-is
fix: confirm with whoever manages the EGO deployment whether signing keys are shared across services or per-audience. If shared, add an `audience`/`issuer` check to `jwt.verify` (`verifyEgoJwt.ts`) before relying on this token for authorization

`hasUserWriteAccess` is called ad hoc at three separate call sites (`src/controllers/submission/submit.ts:59`, `commit.ts:60`, `editData.ts:65`) rather than through a seam a new write path can't bypass by omission. A fourth write controller added later is authorized by nobody unless its author remembers to add the call, and nothing fails if they don't; the failure mode is silent, not an error. `verifyJwtToken` (`src/middleware/verifyEgoJwt.ts`) calls `jwt.verify(...)` and discards its return value, then separately calls `jwtDecode(token)` on the raw token to get the payload actually used downstream. Not currently exploitable, since decode only runs after verify succeeds on the same bytes, but it's a fragile coupling: if verification is ever made conditional, reordered, or its error caught and swallowed, the decode keeps working and silently supplies unverified data
fix: use `jwt.verify`'s own return value (it returns the decoded, verified payload) instead of a second, separate `jwtDecode` call. One-line change, no behavior change today, removes a future footgun

Token verification trusts exactly one public key (`AUTH_PUBLIC_KEY`, a single PEM), with no key set, no rotation overlap and no per-issuer keys. Any change of signing authority is therefore all-or-nothing per deployment: during a migration away from EGO, including through a transitional token-minting service, this service cannot accept tokens from both issuers at once, and a routine key rotation has no overlap window either. Related to the missing `iss`/`aud` check above but separate from it: that one concerns which tokens a key admits, this one how many keys can be trusted at a time
fix: accept a configured set of verification keys, each tied to an expected issuer, so two signing authorities can be trusted through a cutover and a rotation can overlap. Pairs naturally with adding the issuer and audience check
standalone: yes

The requester's identity is their email address. Verification sets the username from the token's `context.user.email` at a single point (`src/middleware/verifyEgoJwt.ts`), and that string is what Lyric stores as `created_by`/`updated_by` on submissions, submitted data, the submitted-data audit table, dictionaries, categories and dictionary migrations. Exposure of that identity on reads is covered by the read-authorization requirements above. Emails change and can be reassigned, which makes them a poor durable key. Switching the source to a stable identifier, such as the token's `sub`, which nothing reads today, is one line for new writes but carries two hazards in existing data: Lyric finds a user's open submission by matching `created_by` against the username, so a submission opened under the old value is stranded at cutover; and the audit table and dictionary migrations are historical records, so rewriting their `created_by` rewrites who did what
fix: if the identity key changes, drain or migrate open submissions atomically with the switch, and decide deliberately whether historical audit rows are rewritten, kept under the email with both forms resolved for display, or given an identifier column alongside. Needs coordination with Lyric and with the access-control work motivating the change
